# Internationalisation (i18n)

| Last updated | 2026-05-06 |
|--------------|------------|
| Scope        | Investor-demo site (`investor-demo/web`) |
| Locales      | English (`en`), French (`fr`), German (`de`) |

## Status

i18n in Vault Genome is currently **partial coverage**. The
infrastructure (dictionary, locale switcher, fallback semantics) is
in place; the translated content is limited to high-traffic strings
on the homepage:

- Navigation labels
- Hero title / subtitle / CTAs
- Footer

Long-form content (compliance crosswalk, threat model, reference
designs, ADRs) remains English-only.

## Why partial coverage

Two reasons:

1. **Translation accuracy in regulated terminology.** Words like
   "doctrinal invariant", "tamper-evident audit chain", or
   "TEE-bound sealing" carry technical and legal meaning. A
   machine translation that gets them wrong creates worse buyer
   confusion than English-only would. We commit to translate this
   content only when a native speaker with cybersecurity/regulatory
   background reviews each entry.
2. **Refactor cost vs. signal.** Full route-based i18n
   (`/fr/...`, `/de/...`) requires moving every page under a
   `[lang]` segment. That refactor produces noise on every diff
   for years. We're holding off until customer demand justifies it.

## How it works

### Dictionary

`investor-demo/web/src/lib/i18n/dict.ts` exports:

- `Locale` — type alias (`"en" | "fr" | "de"`)
- `SUPPORTED_LOCALES`, `DEFAULT_LOCALE` — constants
- `LOCALE_LABEL` — locale's name in its own language (Français, Deutsch)
- `t(key, locale)` — dictionary lookup with English fallback
- `resolveLocale`, `isSupportedLocale` — helpers for query params / cookies
- `translationCoverage()` — admin helper returning per-locale key count

### Locale switcher

`investor-demo/web/src/components/LocaleSwitcher.tsx` is a small
client-side dropdown that:

- Shows the user's currently-selected locale
- Persists the choice in `localStorage` under `vg-locale`
- Updates `document.documentElement.lang` so screen readers and
  locale-aware browser features pick up the change

It does NOT route to a `/fr/...` URL. The first paint always renders
English; the switcher rehydrates with the stored choice and
re-renders the (currently small) localised slice.

### Adding a translated string

1. Add the key + English copy to `dictionaries.en` in `dict.ts`.
2. Add the same key with French + German translations to
   `dictionaries.fr` and `dictionaries.de`. Use machine translation
   if no native speaker is available — mark with the `[MT]` comment
   so the next reviewer knows to verify.
3. Replace the hard-coded English string in the component with
   `t("your.key", lang)`.
4. Run `vitest run src/lib/i18n` to confirm coverage parity.

### Adding a new locale

1. Add the locale code to `SUPPORTED_LOCALES`.
2. Add a `LOCALE_LABEL` entry.
3. Populate `dictionaries[locale]` with translations of every
   existing English key.
4. Update this document's coverage table.

## When to expand

Trigger conditions for moving from "partial" to "full" i18n:

- A specific buyer commits to a deployment in their language.
- An EU regulator (BaFin, ACPR, AMF) requires localised compliance
  evidence.
- A native FR/DE-speaking engineer joins the team.

Until then, English remains the source of truth and the localisation
serves as a "we recognise you exist" signal for European visitors —
not a complete localisation product.

## Future direction

Full route-based i18n via Next 16 app router's `[lang]` dynamic
segment, once one of the trigger conditions above is met. The
existing `dict.ts` interface is designed to remain compatible with
that refactor — only the URL routing and `getLayout`-style metadata
will change.

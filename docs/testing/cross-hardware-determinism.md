# Cross-Hardware Determinism — Measured Evidence

**Date:** 2026-09-13
**Platforms:** GCP Confidential VMs — AMD `EPYC 7B13` (Milan, `n2d`) vs Intel
`Xeon @ 2.60GHz` (Ice Lake, `n2`), `us-central1`.
**Method:** the same seeded transformer block (attention + FFN + LayerNorm,
`d=256`, `L=64`, RNG seed 42) run on each architecture; SHA-256 (first 20 hex)
of the output tensor's raw little-endian bytes emitted to the serial console in
triplicate and majority-voted. Weights are generated by an architecture-neutral
RNG on CPU so both machines receive identical inputs.

This is the empirical basis for **ADR 0008** (the numerical equivalence gate)
and for the "determinism ladder" in the reference design. Hashes are copied
verbatim from the serial-console captures.

## Results

### XARCH2 — matmul / GEMM + integer, pinned numpy 1.26.4, threads 1 vs 4

| Machine | f32 (t=1) | f32 (t=4) | f64 (t=1/t=4) | integer |
|---|---|---|---|---|
| AMD EPYC 7B13   | `5150816385db30aa6ce4` | `5150816385db30aa6ce4` | `a8e6ff56585a6d3d536b` | `52bee5c0b137cb80875d` |
| Intel Xeon IceLake | `5150816385db30aa6ce4` | `5150816385db30aa6ce4` | `a8e6ff56585a6d3d536b` | `52bee5c0b137cb80875d` |

**Finding:** GEMM output is **byte-identical across architecture AND thread
count** (t1 == t4, AMD == Intel) for f32, f64, and integer. BLAS tiles over the
output, so the reduction order is thread-independent. Determinism is free here.

### XARCH4 — mixed-dtype promotion (f32 accumulated via f64), pinned numpy 1.26.4

| Machine | f32 (mixed) | f64 |
|---|---|---|
| AMD EPYC 7B13   | `148a31eab68ff5216a4b` | `28f09d8595c3b56ff4cd` |
| Intel Xeon IceLake | `38e6cf5f898a603b776f` | `28f09d8595c3b56ff4cd` |

**Finding:** pure f64 is identical across arch (`28f09d…`), but the **mixed-dtype
f32 path DIVERGES** (`148a…` vs `38e6…`). The divergence is an artifact of
dtype promotion (f32 values promoted to f64 in intermediate ops), which resolves
differently per architecture. **Avoidable** by never mixing dtypes in the
canonical path.

### XARCH5 — pure consistent-dtype f32, naive vs fixed-order reduction, numpy 1.26.4

| Machine | naive f32 | deterministic-order f32 |
|---|---|---|
| AMD EPYC 7B13   | `af3921ae52e2c175b9da` | `8da8af1bc4d7a9bca19d` |
| Intel Xeon IceLake | `af3921ae52e2c175b9da` | `8da8af1bc4d7a9bca19d` |

**Finding:** with a **consistent dtype**, pure f32 is **byte-identical across
arch** (`af3921…` == `af3921…`). This isolates XARCH4's divergence to mixed-dtype
promotion specifically, not to f32 arithmetic in general. (Cross-check: this
`af3921…` equals XARCH6's numpy-1.26.4 f32 below; XARCH4's f64 `28f09d…` equals
XARCH6's numpy-1.26.4 f64 — the runs are internally consistent.)

### XARCH6 — version drift: numpy 1.26.4 (apt, system OpenBLAS) vs 2.1.0 (pip wheel)

| Machine | v1.26.4 f32 | v1.26.4 f64 | v2.1.0 f32 | v2.1.0 f64 |
|---|---|---|---|---|
| AMD EPYC 7B13   | `af3921ae52e2c175b9da` | `28f09d8595c3b56ff4cd` | `41bb4571bb4c3b4b2d4b` | `64c2bf12d9eb75bad2a0` |
| Intel Xeon IceLake | `af3921ae52e2c175b9da` | `28f09d8595c3b56ff4cd` | `73bea2d0987e8ff7b6b6` | `4ed5516693fe8caaaa38` |

**Finding:** under **pinned numpy 1.26.4** the output is byte-identical across
arch. Under **numpy 2.1.0's pip wheel** (a different bundled BLAS) it diverges
BOTH across version (1.26.4 ≠ 2.1.0 on the same machine) AND across architecture
(AMD `41bb…` ≠ Intel `73be…`). BLAS build/version is the dominant fragility.

## Conclusions (feeding ADR 0008)

1. **matmul + integer are deterministic across arch and threads by
   construction** — no special handling needed.
2. **Pure, consistent-dtype float** is byte-identical across arch **only under a
   pinned runtime version**.
3. **Two things break cross-arch byte-identity**, in order of importance:
   - **BLAS build/version drift** — the runtime must be pinned *and attested and
     verified*, not merely pinned by request (a pip wheel silently changes it).
   - **Mixed-dtype promotion** — avoidable in the canonical compute path.
4. Therefore byte-`EXACT` reconstruction is achievable but **build-fragile**;
   the honest reference must not *assume* it. The **numerical equivalence gate**
   (ADR 0008) is what lets a faithful-but-not-bit-identical reconstruction be
   admitted as `EQUIVALENT` while a genuinely wrong one is blocked — and the
   determinism ladder (pinned+attested+verified runtime → deterministic portable
   kernels → fixed-point) is what makes a passing verdict reliably reachable.

## Reproduction

Probe scripts: `geoar-verifier/gcp-cvm/probe-xarch{2,4,5,6}.sh` (launch a
Confidential VM on each `--min-cpu-platform`, run the block, emit hashes to
`/dev/ttyS0`). Serial console captured with `gcloud compute instances
get-serial-port-output` and decoded/majority-voted with
`tools/decode_console.py`. XARCH3 (a torch-based variant) is intentionally absent
— the torch install failed and produced empty results, which is why the suite
pivoted to a pure-numpy transformer that could be validated locally first.

# The acceptance trial of v0.10.0 — every kit on the signed release's own bytes

**What this is.** After v0.10.0 (2026-10-23) every hardware kit of the
tree is run again, unmodified, from a checkout of the signed tag, and the
product binaries each kit builds and uploads are the release's own bytes:
the same SHA-256 as the signed assets. Every run's record is committed under
the kit's `evidence/` as always, and the runner's record of the run under
[`scripts/hardware-test/trial/evidence/`](../scripts/hardware-test/trial/evidence/).
A trial passes when its run reaches the criterion its claim states in
[`VERIFIABLE-CLAIMS.md`](../VERIFIABLE-CLAIMS.md). Nothing here is a new
claim: it is every claim checked against the code that is released, on the
hardware that is available.

**Why.** A buyer's first question is whether what is shipped does what the
claims say. The release kits answer it for the deployment from the assets
(C27); this trial answers it for every other capability — the TDX and Azure
paths, the confidential GPU, the delegated verifier, the drills, the
profiles and the certified module, the reference design, the Nitro enclave
— on the binaries a customer downloads.

**How it is run.** [`scripts/hardware-test/trial/run.sh`](../scripts/hardware-test/trial/run.sh)
runs one kit from a lane, a worktree detached at the tag, and:

1. checks that the lane is the tag — HEAD at the tag's commit, the tag's
   signature good under `.github/allowed_signers`, no tracked file changed;
2. gives the kit's own `go build` the release's link flags through
   `GOFLAGS` — taken from the tag's Makefile as `release.yml` calls it, with
   `VERSION` the tag and `COMMIT` the full commit — and git's
   `status.showUntrackedFiles=no` through the environment: Go stamps a
   build `vcs.modified` when `git status` lists anything, untracked files
   included, and a kit's own evidence directory is untracked while it runs;
   the tracked tree is what step 1 checked, and a change to it still marks
   the build modified;
3. builds the five release binaries and their `-fips` variants the way the
   kits build them (`CGO_ENABLED=0 GOOS=linux GOARCH=amd64 go build
   -trimpath`) and requires every one to equal its signed asset — the
   environment is the release's, or nothing runs (`lane-build.txt`);
4. runs the kit with the arguments its claim's Reproduce line gives;
5. holds every `inputs.sha256` the kit wrote — the digests of what it
   uploaded to the guests — to the asset list (`release-bytes.txt`) and
   copies the kit's evidence into the tree, compared byte for byte.

The asset list is the release-deploy kit's record of the published release
(`release-deploy/evidence/20261023T201852Z/verify/assets.sha256`), taken
after every pair, every bundle and every provenance verified; that run and
the images' run are T9. Kits that share nothing run in parallel, within the
test project's quotas; a kit that measures the host runs with no other CPU
kit in its cloud. A failure is not edited away: the row says what failed,
the fix is a pull request of its own, and a new row says what the next run
did.

## Results

All thirty-two trials passed, between 2026-10-23 21:48Z (T1) and
2026-10-24 08:15Z (the last of T22's soaks), in forty-seven runs. Before
every run the lane built the ten release binaries to the signed assets'
bytes (47 of 47, `lane-build.txt`); of the 206 product binaries the kits
uploaded and recorded, 202 are the release's own files by SHA-256 — the
`-fips` assets wherever `VG_FIPS=1` — and the four that are not are
T28's, whose kit links with flags of its own. Two rows ran more than
once: T17, because the first run's deletion of host A landed after A had
finished the job in flight, so nothing was lost and nothing could be
resumed (the second run resumed A's lost job itself); and T24, because
the first key-release start got no n2d-standard-2 in us-central1-b and
ran in us-central1-c. One defect of the runner was found and fixed
(`1ac68993`: the directory of another run of the same kit is left out of
a run's record). Observations for the kits, none of them a failure: the
failover kits record the destination's binaries but not the authority's
(T13–T16), `gcp-failover` (T11) and `failover-negatives` (T12) record
neither, and `gcp-drill` (T18) not its `acpctl` — for those the runner's
lane build stands; the `azure-cgpu` kit's last line says "the 7B genome"
whatever the base; four `*.out` provisioning summaries fall under the
ignore rules and are added past them here. The quotas that bounded the
parallelism — 32 vCPUs and one GPU for the whole GCP project, 16 N2D per
region, one confidential H100 (40 vCPUs) in westeurope — are the test
accounts', not the protocol's. The trial's thirteen new genuine SEV-SNP
reports joined the corpus of ADR 0034: 55 reports from 27 chips, every
one read alike by the product and by Google's go-sev-guest.
